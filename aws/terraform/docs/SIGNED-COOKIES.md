# CloudFront signed cookies, in depth

Step 3 wired up the pieces (`signing-key.tf`) but the *mechanism* — how a cookie
actually convinces CloudFront to let a request through — is worth understanding on
its own, separately from the Terraform that provisions it.

## The problem this solves

`/movie/*` is video content behind a paywall. Anyone with the URL could otherwise
watch it. CloudFront needs a way to check, on every single request, "does whoever is
asking have permission right now" — without hitting your origin (S3) to ask, and
without you running a server to check on every request either. Signed cookies are
CloudFront's built-in answer.

## The core idea: asymmetric signing, same shape as a JWT

If you've used JWTs, this is the same trust pattern:

- Something you control **signs** a claim with a **private** key.
- The verifier (here, CloudFront itself, at every edge location worldwide) checks the
  signature with the matching **public** key.
- Only the private key holder can produce a valid signature; anyone can verify one.

Concretely:

- **The private key** — generated by `tls_private_key` in `signing-key.tf`, then
  stored in SSM Parameter Store (`aws_ssm_parameter`, `SecureString`). Nothing signs
  with it yet — that's Step 5's Lambda. It must never leave SSM or get committed
  anywhere; whoever holds it can mint a valid "let this request through" claim.
- **The public key** — the same keypair's public half, registered with CloudFront via
  `aws_cloudfront_public_key`. CloudFront now knows "here's a key I recognize."
- **The key group** — `aws_cloudfront_key_group` wraps one or more public keys into a
  named set. This is what actually gets attached to a cache behavior
  (`trusted_key_groups` on `/movie/*`), not the public key directly. CloudFront's
  rule for a gated behavior: *any* request must carry a signature verifiable by *some*
  key in the attached group.

## What a signed cookie actually contains

CloudFront doesn't want a bare signature — it wants a signature **over a policy**
describing exactly what's being permitted. That policy is a small JSON document,
e.g. (this is the *custom* policy shape, which is what Step 5 will use, since a later
step adds an IP condition):

```json
{
  "Statement": [{
    "Resource": "https://<dist-domain>/movie/*",
    "Condition": {
      "DateLessThan": { "AWS:EpochTime": 1799999999 },
      "IpAddress": { "AWS:SourceIp": "203.0.113.4/32" }
    }
  }]
}
```

Signing produces three values, sent to the browser as three separate cookies:

- `CloudFront-Policy` — the policy JSON, base64-encoded (CloudFront's own base64
  variant: `+`→`-`, `=`→`_`, `/`→`~`, not standard base64).
- `CloudFront-Signature` — an RSA-SHA1 signature of that policy, made with the
  **private** key, same encoding.
- `CloudFront-Key-Pair-Id` — the id of the `aws_cloudfront_public_key` resource that
  matches which private key signed it. This is how CloudFront knows *which* public
  key, out of potentially several in the trusted key group, to verify against.

## What CloudFront does on every request to a gated behavior

1. Sees the request matches an `ordered_cache_behavior` with `trusted_key_groups` set
   (that's `/movie/*`, since Step 3).
2. Looks for the three cookies above. Missing any of them → immediate `403`, no
   further checks. **This is exactly why the whole path returns `403` right now** —
   nothing has signed anything yet, so no request can ever have these cookies.
3. If present, uses `CloudFront-Key-Pair-Id` to find the matching public key —
   rejecting immediately if that key isn't in this behavior's trusted key group.
4. Verifies `CloudFront-Signature` against `CloudFront-Policy` using that public key.
   Tampering with the policy (e.g. editing the expiry) invalidates the signature —
   this is what actually makes the scheme trustworthy, not the cookie names.
5. Decodes the policy and checks its conditions itself — expiry (`DateLessThan`) and,
   later, the IP match. A validly-signed but *expired* policy still fails here.
6. Only if every step passes does CloudFront forward the request to the origin (S3).

None of this touches your origin or your infrastructure per-request — it's fully
evaluated at the CloudFront edge location closest to the viewer, which is the whole
performance point of doing it this way instead of, say, a Lambda@Edge check on every
request.

## Canned vs. custom policy (relevant from Step 5 onward)

CloudFront supports a simpler "canned" policy (just an expiry, no other conditions)
as a shortcut when you only need `DateLessThan`. This project uses the **custom**
policy format from the start, because milestone-1's Lambda embeds an `IpAddress`
condition too, and canned policies don't support that. Nothing in Step 3's
infrastructure differs between the two — this choice only affects the JSON that gets
signed in Step 5.

## What's real right now vs. what Step 5 adds

As of Step 3: the *lock* exists (key group attached, enforcement is live — see the
`server: AmazonS3` → `server: CloudFront` header flip in the README's Step 3
gotchas), but there is no *key* yet. Nothing in this repo can produce a valid
`CloudFront-Signature`. That's deliberate — Step 5 is the Lambda that reads the
private key back out of SSM and does the actual `crypto.createSign('RSA-SHA1')` call
described above.
